# T.9.1 — Auditoria completa de IA no app

> Modo: read-only. Nenhum arquivo do código foi alterado.
> Escopo: src/, functions/, server.ts, .env.example. Sessão única.

---

## TL;DR (sumário executivo)

- **Provider único em produção**: OpenRouter, via proxy Express em `server.ts` → `/api/ai`. Sem chamada direta do front a OpenRouter ou outros providers.
- **Cliente único de transporte**: `athenaClient` (`src/features/athena/services/athenaClient.ts`). Faz `chat()` (3 retries em network error) e `streamChat()`. Timeout 30s na conexão inicial.
- **Fachada ampla**: `aiService` (`src/services/aiService.ts`) com ~30 métodos cobrindo praticamente todas as superfícies do app. **95% chama `DEFAULT_OPENROUTER_CHAT_MODEL` (Gemini 2.0 Flash free)**. 4 métodos usam `GEMINI_PRO.id` direto (`socraticDebate`, `generateMastermindResponse`, `generateOracleProphecy`, `generateStudyPlan`).
- **Bypass da fachada**: 5 superfícies (`Redacao`, `DocumentAnalyzer`, `QuestionsView`, `VideoSummarizer`, e o chat principal via `useAthena`) chamam `athenaClient.chat()` direto em vez de via `aiService`. Não é bug — é inconsistência arquitetural.
- **Roteamento por tarefa = morto**: `TASK_STRATEGIES` (chat/redacao/matematica/...) está definido em **dois** arquivos (`src/config/openRouter.ts` e `functions/src/ai/config.ts`) e **nenhum dos dois é importado em runtime de produção**. O app **não tem fallback automático entre modelos** — apenas 3 retries no mesmo modelo em caso de network error.
- **3 fontes de verdade pra modelos**: `src/config/openRouter.ts` (canonical, usado pelo runtime), `src/config/aiModels.ts` (legacy, usado pela UI ModelSelector), `src/features/athena/constants/models.ts` (lista paralela do chat Athena).
- **2 sets de prompts modulares órfãos**: `src/config/aiPrompts.ts` (`STUDIO_FLOW_PROMPTS`) e `src/services/ai/prompts.ts` (`SYSTEM_PROMPTS`). Nenhum é importado em produção.
- **Diretório `src/services/ai/` inteiro está morto** (`models.ts`, `prompts.ts`, `schemas.ts`). Schemas com tipos JSON estruturados nunca foram conectados.
- **Diretório `functions/src/ai/`** (Firebase Cloud Functions com fallback inteligente entre 9 modelos) está **completamente desconectado do app** — o app roda Express, não Firebase Functions.
- **Ponto cego mais grave**: `DocumentAnalyzer` e `VideoSummarizer` mandam só URL/nome de arquivo pra LLM **sem extrair conteúdo**. O modelo alucina com base em prompt placeholder. Tecnicamente "funciona" (retorna JSON) mas a resposta não tem relação com o documento real.
- **Recurso fake**: `aiService.generateAudio` retorna string hardcoded `"audio_data_placeholder"`. Usado em `Flashcard.tsx` e `NotesView.tsx`.

## ETAPA 3 — Configuração

### a) `.env.example`

```
VITE_SUPABASE_URL=...
VITE_SUPABASE_ANON_KEY=...
OPENROUTER_API_KEY=your-openrouter-key       # usado pelo server.ts
VITE_OPENROUTER_API_KEY=your-openrouter-key  # fallback
```

- **Apenas OpenRouter está documentado**. Sem `VITE_DEEPSEEK_API_KEY`, `VITE_OPENAI_API_KEY`, `VITE_ANTHROPIC_API_KEY`. Coerente com o fato de tudo passar pelo OpenRouter.

### b) Modelo default

- Definido em `src/config/openRouter.ts` linha 74:
  ```ts
  export const DEFAULT_OPENROUTER_CHAT_MODEL = AI_MODELS.GEMINI_FLASH.id;
  // → "google/gemini-2.0-flash-exp:free"
  ```
- Também referenciado em `server.ts` (linha 7) como fallback do proxy se `model` não vier no body.

### c) Fallback / resiliência

- **Servidor (`server.ts`)**: 1 chamada por request ao OpenRouter, sem fallback de modelo. Se `OPENROUTER_API_KEY` ausente → retorna 500 com mensagem clara. Timeout 120s upstream.
- **Client (`athenaClient`)**: 3 retries só em `AbortError` / `Failed to fetch` / `NetworkError`. **Não faz fallback de modelo** se OpenRouter retornar 429 / 503 / "model unavailable" — propaga erro.
- **`useAthena`**: erro vira `toast.error(error.message)` (sonner). Nenhuma superfície fora do chat principal exibe erro pro usuário de forma amigável — a maioria só faz `console.error` e devolve `null` ou string vazia.
- **`TASK_STRATEGIES` (fallback inteligente entre 4-5 modelos)**: definido em 2 lugares (`config/openRouter.ts` e `functions/src/ai/config.ts`) e **NÃO é importado/usado em runtime**. Recurso projetado mas nunca conectado.

### d) Rate limiting / cache

- **Nenhum**. Sem rate limit no proxy, sem cache de respostas. Gemini Flash free do OpenRouter tem limites próprios (rpm/dia) que podem ser atingidos.

### e) Auth

- **Server**: nenhuma auth no `/api/ai`. Qualquer cliente que conheça o endpoint pode usar. ⚠️ Risco de abuso se exposto publicamente.
- **Firebase Function paralela** (`chatWithAI` em `functions/`): tem `if (!context.auth)` rejeitando não-autenticados — mas não está em uso.

## ETAPA 5 — Recomendação de arquitetura

### 5.1 — Diagnóstico arquitetural

1. **Existe um entry point único?** Sim, em transporte (`athenaClient` → `/api/ai`). Não, em fachada — `aiService` cobre 80% mas 5 superfícies bypassam direto pra `athenaClient`.
2. **Providers misturados?** Não. Tudo é OpenRouter via proxy. Mas há **três diretórios paralelos de IA** (`src/services/`, `src/services/ai/`, `src/features/athena/`, `functions/src/ai/`) — três sem nada e um (Firebase) totalmente desconectado.
3. **Estado**: a infra está **funcional mas confusa**. Maioria das superfícies funciona; o problema é dívida técnica acumulada — código morto, duplicação, gambiarras pontuais.

### 5.2 — Arquitetura ideal proposta (futura)

```
┌────────────────────────────────────────────────┐
│  Client (React)                                │
│                                                │
│  Componentes ──► aiService (fachada única)     │
│                       │                        │
│                       ▼                        │
│                  athenaClient (transporte)     │
│                       │                        │
└───────────────────────┼────────────────────────┘
                        ▼
                  /api/ai (server.ts)
                        │
                        ▼  com TASK_STRATEGIES
                   OpenRouter
                        │
            ┌───────────┼────────────┐
            ▼           ▼            ▼
        Gemini Flash  Gemini Pro  Deepseek R1  ...
        (chat)        (redação)   (matemática)
```

**Princípios:**
1. **`aiService` como única fachada** — todo componente chama `aiService.X(...)`. Zero `athenaClient.chat` direto em componente. `aiService` faz roteamento de modelo por tarefa.
2. **`athenaClient` só faz transporte** — sem lógica de prompts, sem escolha de modelo. Recebe `{ messages, model }` e fala com `/api/ai`.
3. **`server.ts` aplica `TASK_STRATEGIES`** — se body tiver `task: 'redacao'`, server tenta `Deepseek R1 → Gemini Pro → Gemini Flash` na ordem. Centraliza fallback no back, fora do code path do front.
4. **Uma única fonte de verdade pra modelos** — `src/config/openRouter.ts`. Apaga `src/config/aiModels.ts`, `src/services/ai/models.ts`, `src/features/athena/constants/models.ts` (ou converte em adapter sobre o canonical).
5. **System prompts modulares centralizados** — escolhe um único arquivo (sugestão: `src/features/athena/prompts/systemPrompts.ts`, já em uso). Apaga `src/config/aiPrompts.ts` e `src/services/ai/prompts.ts`.
6. **Structured output via JSON Schema** — usar `response_format` da OpenRouter quando o modelo suporta, ou validar o JSON com Zod no client em vez de `replace(/```json/, '')` + `JSON.parse`. Schemas já existem em `src/services/ai/schemas.ts` (morto) — reaproveitar.
7. **Loading/error states padronizados** — hook `useAIRequest<T>(fn)` com `{ data, loading, error, retry }`. Cada superfície usa o mesmo hook.
8. **TTS real** — substituir `generateAudio` placeholder por integração com OpenAI TTS, ElevenLabs, ou browser SpeechSynthesis (free).

### 5.3 — Top 5 superfícies prioritárias pra corrigir

Critério: **impacto no usuário × esforço de fix**.
